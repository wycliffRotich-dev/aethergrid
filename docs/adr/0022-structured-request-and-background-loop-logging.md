# ADR 0022: Structured Request and Background-Loop Logging

## Status

Proposed

## Context

The README's "What's Next" lists structured logging as outstanding hardening work, alongside the rate limiting closed by ADR 0021. Today, logging in this codebase consists of exactly one call site: `logger.exception(...)` inside `_run_cluster_loop` in `app/presentation/api.py`, using an unconfigured `logging.getLogger(__name__)`. There is no formatter, no handler configuration, and no logging anywhere on the request path. `require_api_key` and `require_rate_limit` raise `HTTPException` directly with no record of who was denied, or of any request that succeeds.

Two axes were considered independently, mirroring how ADR 0021 was scoped: what gets logged, and how it's wired into the request lifecycle.

**What gets logged.** The system has exactly one authenticated identity concept, `ApiKey`, already established in ADR 0015 and reused as the rate-limit key in ADR 0021. The same identity is the natural correlation key for logs. ADR 0015 chose opaque, server-issued tokens specifically so a leaked credential could be revoked without a JWT-denylist workaround. A system that then logs the raw bearer token defeats that property outright, since the token itself becomes recoverable from log storage, typically a lower-trust, higher-retention surface than the primary datastore. So: `caller.id` (the `ApiKey`'s UUID) is logged; the raw `Authorization` header value is never logged, at any log level, including on the `401` path where `require_api_key` fails before a caller identity exists. That failure is logged with `caller_id=None`, not the attempted key, not even truncated, since a truncated key is still a partial oracle for a brute-force or credential-stuffing check.

**How it's wired in.** `require_api_key` and `require_rate_limit` are both FastAPI dependencies chained via `dependencies=[Depends(...), Depends(...)]` at the `APIRouter` level (see `app/presentation/routers/jobs.py`), not ASGI middleware. This was evaluated on its own merits. ASGI middleware runs outside FastAPI's dependency resolution graph, before the framework has parsed the `Authorization` header into a caller identity. Using middleware for request logging would mean either re-parsing and re-validating the header a second time, duplicating and risking drift from `require_api_key`'s own logic, or logging every request without caller identity and correlating it back in afterward. A yield-style FastAPI dependency, by contrast, can depend on `require_api_key` the same way `require_rate_limit` already does, get `caller.id` for free, and run its logging after the handler via `try/yield/finally`, through the same mechanism this codebase already trusts for every other cross-cutting request concern. FastAPI runs a yield-dependency's teardown code even when the handler raises, including `HTTPException` raised inside the endpoint such as `JobNotFoundError` producing a 404, so this also correctly logs failed requests, not only successful ones.

The background cluster loop (`_run_cluster_loop`, `ReconciliationLoop`) is a separate execution path with no request, no caller, and no FastAPI dependency graph to hook into. A request-logging dependency does not, and cannot, cover it. Leaving it out of scope silently would repeat the exact half-solved-problem shape this codebase's own ADRs (0012, 0018) explicitly reject: building a capability and leaving an adjacent, obviously related gap unaddressed without saying so.

## Decision

- A new `RequestLoggingService` in `app/application/services/`, framework-agnostic like every other application service in this codebase, no FastAPI import, exposing a single method that accepts structured fields: `method`, `path`, `caller_id: str | None`, `status_code`, `duration_ms`, and emits one log record via the standard `logging` module. It does not decide log format; it only decides what fields exist.
- A `log_request` yield-dependency added to `app/presentation/auth.py`, depending on `require_api_key` for `caller.id` so it necessarily runs after authentication, consistent with `require_rate_limit`'s own ordering. It records a monotonic start time, yields to let routing and handler execution proceed, then logs on the way back out via `RequestLoggingService`, wrapped in its own `try/except` so a logging failure can never mask or replace the response the handler already produced.
- `log_request` is added to every router's `dependencies=[...]` list, after `require_api_key` and `require_rate_limit`, the same way `require_rate_limit` itself was added uniformly across every router in ADR 0021, not applied selectively.
- Logging is configured once, at startup, in `app/presentation/api.py`, the composition root for the FastAPI app itself, using the standard library's `logging` module with a JSON-emitting `Formatter`, no new third-party dependency. A dedicated JSON logging library was considered and rejected for the same reason ADR 0021 rejected Redis: it solves a problem, high-volume structured log parsing at scale, this system does not have yet at single-process scale, at the cost of a dependency it does not otherwise carry.
- The raw `Authorization` header value, and the raw API key string in any form, full or truncated, are never logged, at any log level, on any code path, including authentication failures. Only `caller.id`, post-authentication, or the literal string `unauthenticated`, pre-authentication or on auth failure, is logged.
- The background cluster loop's existing `logger.exception(...)` calls are brought into the same structured format and logger configuration as request logging, in this same change, not deferred, since both are "make existing and new logging structured," not two different features. This does not add new log statements to the cluster loop's business logic, only formats the ones that already exist.
- Log level: request completions log at `INFO`; `401`/`429` denials log at `WARNING`; unhandled exceptions, already the case in the cluster loop, log at `ERROR` with `exc_info`.

## Consequences

Every request and every background-loop error now produces a structured, parseable log line with consistent fields, closing the gap the README named.

Log volume becomes proportional to request volume for the first time. At today's single-operator, single-process scale this is inconsequential, but if request volume grows significantly before the multi-instance deployment work in the README's "What's Next" happens, log volume, and where those logs are stored or shipped, becomes a cost that hasn't been sized here. This ADR does not address log shipping, retention, or aggregation, that is deployment infrastructure, not application code, and is out of scope the same way ADR 0021 scoped out Redis.

Error tracking, such as Sentry-style exception capture and alerting, is a related but distinct concern from request and error logging. This ADR does not cover it and it should be its own ADR (0023) rather than folded in here, since alerting has different failure modes, a flaky third-party ingestion endpoint should never be able to block or slow a request, that deserve their own dedicated reasoning.

JSON serialization of a log record on every request is synchronous, in-process work added to the request path. Given this codebase already accepts synchronous psycopg calls on the request path today, no async driver, this is consistent with the system's existing performance posture, not a new category of tradeoff, but it is worth naming explicitly rather than assuming it's free.

An unauthenticated caller can still reach `log_request`'s teardown path via `require_api_key`'s own `401`, meaning a caller spamming malformed `Authorization` headers can generate unbounded `WARNING` log writes with no rate limit applied, since `require_rate_limit` runs only after successful authentication. This is a known, named limitation of this decision, not an oversight, and is deferred to a future ADR the same way ADR 0021 deferred multi-instance rate limiting.

If a future ADR moves this system to multiple concurrent instances, per ADR 0021's own noted limitation, per-process log output alone will no longer give a single operator a unified view across instances, the same class of problem ADR 0021 already flagged for its in-memory rate limiter. That is a deployment-shape problem for a future ADR to solve, not a defect in this one.
