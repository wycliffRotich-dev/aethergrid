The problems your team stops having

AI workloads run for a long time on expensive machines, and machines fail. AetherGrid is built so that the failures your team would otherwise catch by hand are handled by the system.

A machine dies mid-job and the work just sits there.

Every job is held through a renewable lease. When the owner stops renewing, reconciliation detects it and returns the job to a healthy worker, with no one stepping in.

Lease ownership (ADR 0005)Continuous renewal (ADR 0014)Reconciliation (ADR 0007)Reclaim and repair (ADR 0011)

The same job runs twice, or a late result overwrites a good one.

Each job has one owner at a time. Lease renewal, release and outcome reports are fenced by lease identity, so a stale worker cannot overwrite the current owner.

Fenced release (ADR 0034)Fenced outcomes (ADR 0036)Fenced renewal (ADR 0038)

GPU hours burn on work that nobody needs any more.

When a job finishes, times out, is cancelled or loses its owner, its command is stopped along with anything it left running.

Kill leftovers (ADR 0079)Owner dies (ADR 0080)Supervisor ends (ADR 0083)

Jobs land on machines that cannot run them well.

Scheduling matches each job to a node on CPU, memory and VRAM together, and a job stays on its own tenant’s nodes. The scheduling policy lives in the domain, where it is easy to read and test.

Best-fit scheduling (ADR 0043)Domain owns scheduling (ADR 0018)Jobs stay on own nodes (ADR 0069)

Several teams or customers share one cluster, and their data must stay apart.

Tenant isolation is enforced in the application and in the database, and the tenant comes from the credential, never from the request.

Isolate by tenant (ADR 0064)Tenant-scoped jobs (ADR 0068)Tenant-scoped events (ADR 0074)

Upgrades feel risky on a system that has to stay up.

Schema changes ship as versioned migrations. Each release is rehearsed against a database from the release before it, and the upgraded schema is compared with a fresh one.

Versioned migrations (ADR 0071)Upgrade rehearsal (ADR 0085)Schema comparison (ADR 0087)

When something goes wrong, nobody can say what happened.

Every job keeps its event history, requests and background loops write structured logs, and errors are tracked, so an operator can see what happened and why.

Event history (ADR 0008)Structured logs (ADR 0022)Error tracking (ADR 0023)

A job cannot start, or runs forever, and nobody finds out.

A job whose command cannot start fails with a clear outcome. Each job carries its execution timeout, and a running job can be cancelled.

Cannot start (ADR 0081)Execution timeout (ADR 0070)Cancel running job (ADR 0029)

Built for the day something breaks

Machines fail, processes linger and releases get rolled out. AetherGrid is designed around those moments.

A worker disappears

Its lease runs out, reconciliation finds the abandoned job, and the job goes back to a healthy worker.

Two workers want the same job

Only the worker holding the lease may act on it, and a worker that loses its lease stops acting as the owner.

A job leaves processes behind

When a job ends, times out or is cancelled, its whole process tree is stopped, not only the first process.

The scheduler runs in two places

The cluster tick runs in one process at a time, so two schedulers never place the same work.

Customers share one database

Tenant isolation is enforced in the application and in the database, so a worker, a job or a lease cannot be tied to another tenant’s records.

You upgrade to a new release

Each release is rehearsed on a database from the one before it: migrate, compare every table and the schema, then start the new API and read the data back.

Technical depth

The guarantees above rest on specific engineering decisions. Each one is written down in a decision record with the reason it was made.

Lease fencing

Release, renewal and outcome reports are fenced by lease identity, not only by worker identity, so a stale worker cannot change a job it no longer owns.

Reconciliation

Bounded-retry reconciliation reclaims work from dead workers, expired leases and offline nodes through one shared reclaim operation.

One scheduler at a time

Scheduler leadership is elected with a PostgreSQL advisory lock, so two scheduler processes never place the same work.

Process supervision

Job commands start under a supervisor that stops the whole process group when the owner dies. Timeouts end with SIGTERM, then SIGKILL.

Tenant boundary in the database

On PostgreSQL, composite keys tie workers and leases to their tenant, and the migration stops with a count if any row crosses tenants or has none.

Layers that are enforced

Domain, Application, Infrastructure and Presentation stay separate, with a test that fails if an import crosses a layer boundary.

Frequently asked questions

What is AetherGrid?

An open-source control plane that keeps AI workloads running when machines fail. It schedules jobs, gives each one a clear owner and recovers work automatically.

What happens when a machine fails mid-job?

The system notices and recovers. Every job is owned through a renewable lease, and when a worker stops renewing it, reconciliation returns the job to a healthy worker. Nobody has to be paged for the routine case.

How do you prevent duplicated work?

Ownership is explicit. Each job has one authorized owner at a time, and recovery is designed so a reclaimed job is not left with two owners.

Can we see it working before we commit?

Yes. A live dashboard is available today and the full source is public. A scoped pilot lets you see it on your own workloads.

Can we inspect the design and the code?

Completely. The source, releases and written architecture decisions are open, so your engineers can verify every claim for themselves.

How is access controlled between teams?

Scoped API keys and tenant isolation keep each team’s jobs, nodes and workers separate.

Will it fit our existing stack?

Yes. AetherGrid focuses on execution ownership and recovery, so it is designed to work alongside tools like Kubernetes, Ray and Temporal rather than replace them.
