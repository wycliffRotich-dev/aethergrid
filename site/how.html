Built for the day something breaks

Machines fail, processes linger and releases get rolled out. AetherGrid is designed around those moments, so each one ends with your work still running.

See it running

A worker disappears

Its lease runs out, reconciliation finds the abandoned job, and the job goes back to a healthy worker. Your work keeps moving and nobody has to step in.

Reconciliation (ADR 0007)Reclaim and repair (ADR 0011)Full reclaim on return (ADR 0039)

Two workers want the same job

Only the worker holding the lease may act on it, and a worker that loses its lease stops acting as the owner. Every job has one clear owner at a time.

Fenced release (ADR 0034)Fenced renewal (ADR 0038)Fenced outcomes (ADR 0036)

A job leaves processes behind

When a job ends, times out or is cancelled, its whole process tree is stopped, not only the first process. Your GPUs go back to useful work.

Kill leftovers (ADR 0079)Owner dies (ADR 0080)Supervisor ends (ADR 0083)

The scheduler runs in two places

The cluster tick runs in one process at a time, so two schedulers never place the same work. A second replica or a rolling deploy waits its turn instead of scheduling against the same nodes.

Advisory lock election (ADR 0078)Tick off the event loop (ADR 0032)

Customers share one database

Tenant isolation is enforced in the application and in the database, so a worker, a job or a lease cannot be tied to another tenant’s records. Each customer stays inside its own boundary.

Isolate by tenant (ADR 0064)Workers and leases (ADR 0075)Jobs stay on own nodes (ADR 0069)

You upgrade to a new release

Each release is rehearsed on a database from the one before it: migrate, compare every table and the schema, then start the new API and read the data back. You upgrade something you have already watched work.

Upgrade rehearsal (ADR 0085)Migrations applied (ADR 0086)New API on upgraded DB (ADR 0088)
