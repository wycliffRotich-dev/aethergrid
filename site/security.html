Security, designed in

Security in AetherGrid is part of the design. Each control below is documented in a public decision record, and the source is open, so your engineers can verify every one of them.

Access control

Every route requires an API key. Keys are scoped, so a key can do only what it was issued to do, and issuance and revocation are controlled by scope and by ownership. Each agent in a fleet uses its own key, and every key is rate limited. Interactive API docs are served only when you enable them.

Scoped keys (ADR 0054)Revocation by ownership (ADR 0056)Rate limiting (ADR 0021)API docs on demand (ADR 0077)

Tenant isolation

Customers share the platform and never share data. Isolation is enforced in the application and in the database, and the tenant comes from the credential, never from the request. It covers API keys, nodes, jobs, workers, leases and events.

Isolate by tenant (ADR 0064)Tenant-scoped jobs (ADR 0068)Tenant-scoped events (ADR 0074)Tenant-scoped workers and leases (ADR 0075)

Execution ownership

Each job has one owner, held through a renewable lease. Lease release, renewal and outcome reports are fenced by lease identity, and reconciliation re-checks the lease at the moment it acts, so a stale worker cannot overwrite the current owner.

Fenced release (ADR 0034)Fenced outcome reports (ADR 0036)Fenced renewal (ADR 0038)Fenced reconciliation (ADR 0052)

Hardened containers

The application container runs read-only with no added capabilities. Credentials stay out of the repository, the hardening checks run in CI, and they are proven able to fail, so a regression is caught before release.

Hardened defaults (ADR 0058)Read-only, no capabilities (ADR 0059)Enforced in CI (ADR 0060)Checks proven to fail (ADR 0061)

Upgrades you can rehearse

Schema changes ship as versioned migrations, and the application checks the schema version when it starts. Each release is rehearsed against a database from the previous release, and the upgraded schema is compared with a fresh one.

Versioned migrations (ADR 0071)Startup schema check (ADR 0072)Upgrade rehearsal (ADR 0085)Schema comparison (ADR 0087)

Observability and audit trail

Every job keeps its event history. Requests and background loops write structured logs, errors are tracked, and liveness is separate from readiness, so operators can see what happened and why.

Event history (ADR 0008)Structured logs (ADR 0022)Error tracking (ADR 0023)Liveness and readiness (ADR 0050)
